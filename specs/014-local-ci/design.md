# Design

Approved on 2026-10-09 by the user's explicit approval of requirements, design and T1–T4. Package/module remain 0.7.0/0.7.

The existing workflow uses `runs-on: ubuntu-24.04`, which selects a hosted VM rather than a portable Docker image. Using an approximate act image would not meet image parity. Instead, keep that host runner and move verification into a Docker container launched by the same repository wrapper that the local Task commands invoke. Checkout and failure-artifact upload remain pinned hosted actions outside the container.

Add a small Python standard-library Docker wrapper and a shared shell entry point under `scripts/`. The wrapper owns one verified Ubuntu 24.04 image reference pinned by digest, forces `linux/amd64`, validates the supported Qt version and checks Docker availability. Resolve the actual image digest during implementation before execution; do not invent a digest or rely on a mutable tag. Both Task aliases and the workflow call this wrapper. Replace the workflow's separate apt/Qt-install/packaging/benchmark steps with that invocation, so provisioning and checks cannot diverge between local and remote execution.

The wrapper makes a Git-aware snapshot of current tracked and nonignored untracked files, including uncommitted edits and tracked deletions. It excludes Git metadata, credential/configuration directories, `.env*`, `.pem` and `.key` files without reading them. Mount that snapshot read-only at a fixed source path and a fresh artifact directory read-write at a fixed output path. Ignored files are not CI inputs. Local outputs live under ignored `build-ci/<qt-version>/<run-id>/`; GitHub supplies an output directory under RUNNER_TEMP for its failure uploader. No host Qt paths, display variables, secrets or Docker socket are mounted inside. Record the selected image, Qt, OS and tool versions alongside console output. Use the existing 35-minute bound and propagate container exit status. Stop only this run's named container on timeout or interruption.

The shell entry point provisions the existing workflow's apt dependencies, Python venv support and utilities needed for user switching. Install the pinned aqtinstall/py7zr into a container-only venv and download the requested official Qt SDK. Then run verification as the caller's numeric UID/GID, with dedicated writable temporary/cache paths and offscreen/Fusion rendering. Retain the existing two-job build parallelism. Invoke `verify-packaging.py` with the container SDK and artifact directory, then execute the existing Release benchmark configure/build/smoke/JSON-validation sequence. Fail promptly and retain outputs; no duplicated packaging implementation.

Digest pinning makes the starting image identical. Apt repository contents and SDK/transitive installer downloads remain external inputs, as in the existing workflow; record versions and document that boundary rather than claiming byte-for-byte reproducibility of every downloaded dependency. No image build or registry publication is required. Docker daemon access and dependency downloads may require execution approval in the assistant sandbox, separately from feature approval.

Documentation adds the two Task commands and prerequisites to README and updates workflow parity claims. No renderer, public API, installed-library dependencies or releases change.
